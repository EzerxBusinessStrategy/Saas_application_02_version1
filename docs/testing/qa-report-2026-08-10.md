## Release-Blocking Finding

### P0 - Permission bypass for privileged roles

`PermissionGuard` currently permits `SUPER_ADMIN`, `TENANT_ADMIN`, and `TENANT_OWNER` before checking the endpoint's declared permissions. The protected endpoint test for a Super Admin with no `platform_configuration.read` permission therefore reaches the repository and returns `503` instead of the required `403`.

Evidence: `apps/backend/test/api/platform-configuration.api.test.ts` fails at `denies a Super Admin without configuration permission`.

This must be fixed in the authorization design before treating backend validation as complete. It was intentionally not changed in this testing-only pass.

## Next.js Cache Recovery

- Root cause: `.next-dev/server/webpack-runtime.js` referenced `vendor-chunks/lodash@4.18.1.js`, but that generated file was absent.
- The stale server on port `3002` was stopped. The generated `.next-dev` directory was quarantined as `.next-dev.corrupt-2026-08-10` and a fresh Next.js development server was started on port `3002`.
- After the rebuild, `GET /login` returned `200`, the missing lodash chunk existed, `/admin` returned its expected unauthenticated `307`, and the real Edge Super Admin login test passed in 25 seconds with no missing-chunk error.

## Live Database Read-Only Check

The configured Supabase PostgreSQL endpoint was inspected in a `BEGIN READ ONLY` transaction. No migration, seed, fixture, workflow action, or cleanup statement was executed.

- The connection is currently the `postgres` database role, not `app_runtime` or `app_readonly`.
- `tenant_memberships`, `membership_roles`, `task_assignments`, `task_work_sessions`, `task_work_segments`, and `auth_session_policies` exist with RLS and `FORCE ROW LEVEL SECURITY` enabled; each has four policies.
- `documents`, `document_recipients`, and `task_notification_outbox` were absent. The associated migrations must be applied before their live workflows can be validated.
- `SET LOCAL ROLE app_readonly` was denied for the configured login. Runtime-role RLS isolation has therefore not been proven against the live database.

To complete live RLS validation safely, use a non-owner `app_runtime` connection plus an isolated approved test tenant. Do not run the disposable Testcontainers migration suite against this shared database.
